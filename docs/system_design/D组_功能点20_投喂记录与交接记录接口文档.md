# D组 功能点20 接口文档：投喂记录与交接记录

| 对应控制器 `FeedingTasksController`、`FeedingRecordsController`、`HandoversController` |
| 对应数据库表 `VOL_SHIFTS`、`VOL_CHECKINS`、`VOL_HANDOVERS` |

## 1. 公共约定

- 请求体与成功响应体使用 `application/json`；控制器返回的业务错误为文本字符串。
- JSON 字段采用 camelCase；所有 ID 均为最长 36 字符的字符串，创建时由后端生成 UUID。
- 日期时间使用 ISO 8601，例如 `2026-08-03T09:30:00Z`。
- 查询列表无数据时返回 `200` 和空数组 `[]`，不是 `404`。
- `POST` 成功返回 `201`、新对象和 `Location` 响应头；`PUT`、`DELETE` 成功返回 `204`，响应体为空。
- 业务状态字符串使用大写英文常量（如 `PLANNED`、`PENDING`），后端比较时大小写不敏感，写入时统一通过 `ToUpperInvariant` 规范化。
- 涉及事务性写入的接口（投喂打卡、交接确认/拒绝/撤销）会在并发状态变化时返回 `409 Conflict`，客户端应刷新后重试。
- `PUT` 是完整更新。除 ID 可省略外，应提交该资源需要保留的全部字段；请求体中若带 ID，必须与 URL 中的 ID 相同。

## 3. 数据结构

### 3.1 VolShift（投喂任务）

对应数据库表 `VOL_SHIFTS`，状态集合由 `ShiftStatuses` 定义：`PLANNED`（已排班）、`ASSIGNED`（待执行）、`IN_PROGRESS`（执行中）、`COMPLETED`（已完成）、`MISSED`（逾期未完成）。

| 字段 | 类型 | POST 必填 | PUT 必填 | 说明 |
|---|---|---:|---:|---|
| `shiftID` | string | 否 | 否 | POST 时忽略并由后端生成；PUT 时如提供，必须与 URL 的 `id` 相同 |
| `volunteerID` | string | 是 | 是 | 负责的志愿者 ID，必须存在 |
| `pointID` | string/null | 否 | 否 | 投喂点 ID；非空时必须存在 |
| `backupVolunteerID` | string/null | 否 | 否 | 备用志愿者 ID；非空时必须存在，且不能与 `volunteerID` 相同 |
| `planStartTime` | datetime/null | 否 | 否 | 计划开始时间 |
| `planEndTime` | datetime/null | 否 | 否 | 计划结束时间，不能早于 `planStartTime` |
| `shiftStatus` | string/null | 否 | 否 | 任务状态，取值见 `ShiftStatuses`；POST 未提供时由后端默认处理 |

### 3.2 VolCheckIn（投喂打卡记录）

对应数据库表 `VOL_CHECKINS`，状态集合由 `CheckInStatuses` 定义：`CHECKED_IN`（已签）、`LATE`（迟到）。

| 字段 | 类型 | POST 必填 | PUT 必填 | 说明 |
|---|---|---:|---:|---|
| `checkInID` | string | 否 | — | 后端生成；本模块不提供 PUT 修改打卡记录的接口 |
| `shiftID` | string | 是 | — | 关联的投喂任务 ID，必须存在 |
| `checkInTime` | datetime/null | 否 | — | 实际签到时间 |
| `longitude` | number/null | 否 | — | 签到经度，范围 `-180`—`180` |
| `latitude` | number/null | 否 | — | 签到纬度，范围 `-90`—`90` |
| `photoUrl` | string/null | 否 | — | 完成情况照片 URL |
| `distanceMeters` | number/null | 否 | — | 与投喂点的距离（米），不能为负 |
| `checkInStatus` | string/null | 否 | — | 打卡状态，取值见 `CheckInStatuses` |

### 3.3 VolHandover（志愿者交接记录）

对应数据库表 `VOL_HANDOVERS`，状态集合由 `HandoverStatuses` 定义：`PENDING`（待确认）、`CONFIRMED`（已确认）、`REJECTED`（已拒绝）、`CANCELLED`（已撤销）。交接对象通过 `relatedType` + `relatedID` 多态引用，目前仅支持投喂任务（`relatedType='SHIFT'`）。

| 字段 | 类型 | POST 必填 | PUT 必填 | 说明 |
|---|---|---:|---:|---|
| `handoverID` | string | 否 | — | 后端生成；本模块的状态变更走专用子路由，不暴露通用 PUT |
| `fromVolunteerID` | string | 是 | — | 发起方志愿者 ID，必须存在，且必须是关联任务的当前负责人 |
| `toVolunteerID` | string | 是 | — | 接收方志愿者 ID，必须存在，且不能与 `fromVolunteerID` 相同 |
| `handoverType` | string/null | 否 | — | 交接类型，如“长期转交”“临时替班” |
| `relatedType` | string | 是 | — | 关联对象类型，目前固定为 `SHIFT` |
| `relatedID` | string | 是 | — | 关联对象 ID（即 `shiftID`），必须存在 |
| `applyTime` | datetime/null | 否 | — | 交接发起时间 |
| `confirmTime` | datetime/null | 否 | — | 交接确认时间，由后端在确认时写入 |
| `handoverStatus` | string/null | 否 | — | 交接状态，新建时后端默认置为 `PENDING` |
| `remark` | string/null | 否 | — | 备注说明 |

### 3.4 请求体附加结构

#### UpdateShiftStatusRequest

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `newStatus` | string | 是 | 新状态，取值见 `ShiftStatuses` |

### 4.6 新增投喂任务

| 项目 | 内容 |
|---|---|
| 接口说明 | 创建新的投喂任务（排班），任务 ID 由后端生成 |
| HTTP Method | `POST` |
| URL | `/feeding-tasks` |

请求体：见 [VolShift](#31-volshift投喂任务)。

```json
{
  "volunteerID": "vol-0001",
  "pointID": "point-feed-0001",
  "backupVolunteerID": "vol-0002",
  "planStartTime": "2026-08-05T09:00:00Z",
  "planEndTime": "2026-08-05T10:00:00Z",
  "shiftStatus": "ASSIGNED"
}
```

| 状态码 | 描述 | 响应体 |
|---:|---|---|
| 201 | 创建成功 | 完整 `VolShift` 对象，其中 `shiftID` 为新 UUID |
| 400 | 数据为空或 `volunteerID` 为空 | 对应的业务错误文本 |
| 400 | 志愿者、备用志愿者或投喂点不存在 | 对应的业务错误文本 |
| 400 | 备用志愿者与负责志愿者相同 | 文本：`备用志愿者不能与负责志愿者相同。` |
| 400 | 状态不合法 | 文本：`无效的任务状态 '{status}'。允许的状态: ...` |
| 400 | 计划结束时间早于开始时间 | 文本：`计划结束时间不能早于计划开始时间。` |

### 4.7 更新任务基本信息

| 项目 | 内容 |
|---|---|
| 接口说明 | 完整更新指定投喂任务的基本信息（不含状态流转） |
| HTTP Method | `PUT` |
| URL | `/feeding-tasks/{id}` |

路径参数：`id` 为待更新任务 ID。请求体结构同 `VolShift`，可省略 `shiftID`。

```json
{
  "volunteerID": "vol-0001",
  "pointID": "point-feed-0001",
  "backupVolunteerID": "vol-0002",
  "planStartTime": "2026-08-05T09:00:00Z",
  "planEndTime": "2026-08-05T10:30:00Z",
  "shiftStatus": "ASSIGNED"
}
```

| 状态码 | 描述 | 响应体 |
|---:|---|---|
| 204 | 更新成功 | 无 |
| 400 | URL 与请求体 ID 不一致 | 文本：`URL 中的 ID 与请求体中的 ID 不匹配。` |
| 400 | 其他业务校验失败 | 对应的业务错误文本 |
| 404 | 任务不存在 | 文本：`未找到 ID 为 {id} 的投喂任务，无法更新。` |

### 5.5 提交投喂打卡（事务）

| 项目 | 内容 |
|---|---|
| 接口说明 | 志愿者完成投喂后提交打卡。后端在同一事务中新增 `VOL_CHECKINS` 记录并把对应 `VOL_SHIFTS` 状态置为 `COMPLETED`。事务失败（任务已完成/已有打卡/状态不允许）返回 `409 Conflict` |
| HTTP Method | `POST` |
| URL | `/feeding-records` |

请求体：见 [VolCheckIn](#32-volcheckin投喂打卡记录)。

```json
{
  "shiftID": "shift-0002",
  "checkInTime": "2026-08-04T09:50:00Z",
  "longitude": 121.50640,
  "latitude": 31.28220,
  "photoUrl": "https://example.invalid/feeding-checkin-002.jpg",
  "distanceMeters": 8.2,
  "checkInStatus": "CHECKED_IN"
}
```

| 状态码 | 描述 | 响应体 |
|---:|---|---|
| 201 | 打卡成功，任务已标记为 COMPLETED | 完整 `VolCheckIn` 对象，其中 `checkInID` 为新 UUID |
| 400 | 数据为空或 `shiftID` 为空 | 对应的业务错误文本 |
| 400 | 关联的投喂任务不存在 | 文本：`投喂任务 ShiftID='{shiftID}' 不存在。` |
| 400 | 打卡状态不合法 | 文本：`无效的打卡状态 '{status}'。允许的状态: CHECKED_IN, LATE` |
| 400 | 经纬度越界 | 文本：`经度 Longitude 必须在 -180 到 180 之间。` 或 `纬度 Latitude 必须在 -90 到 90 之间。` |
| 400 | 距离为负 | 文本：`距离 DistanceMeters 不能为负数。` |
| 409 | 事务失败 | 文本：`该投喂任务已经完成、已有打卡记录或当前状态不允许打卡。` |

### 6.7 提交交接

| 项目 | 内容 |
|---|---|
| 接口说明 | 发起方把关联任务转交给接收方，状态默认 `PENDING`。校验强制要求：发起方必须是关联投喂任务的当前负责人 |
| HTTP Method | `POST` |

请求体：见 [VolHandover](#33-volhandover志愿者交接记录)。

```json
{
  "fromVolunteerID": "vol-0001",
```

## 7. 交叉测试说明

1. 启动 Oracle，并依次执行 `database/create_tables.sql`、`database/insert_demo_data.sql`、`database/queries/task_shift&crowdfunding.sql`。
2. 启动 API：

   ```powershell
   dotnet run --project src/CampusStrayCatSystem.Core/CampusStrayCatSystem.Core.csproj --launch-profile http
   ```

3. 推荐交叉测试覆盖以下场景：

   - 查询空列表（如查询不存在志愿者的任务，应返回 `200 []`）。
   - 按状态筛选时传入非法状态（如 `UNKNOWN`），应返回 `400`。
   - 新增投喂任务时：志愿者不存在、备用志愿者与负责志愿者相同、计划结束时间早于开始时间，应返回 `400`。
   - PUT 更新任务时 URL 与请求体 ID 不一致，应返回 `400`。
   - 提交打卡时：任务不存在、经纬度越界、距离为负、打卡状态非法，应返回 `400`。
   - 对同一任务重复打卡（事务失败），应返回 `409`。
   - 发起交接时：发起方不是任务当前负责人、`relatedType` 非 `SHIFT`、发起方与接收方为同一人，应返回 `400`。
   - 对同一交接连续调用 `confirm`/`reject`/`cancel`，第二次起应返回 `400`（状态非 PENDING）或 `409`（事务失败）。
   - 投喂打卡成功后，再次查询对应任务，确认 `shiftStatus` 已变为 `COMPLETED`。
   - 交接确认成功后，再次查询关联投喂任务，确认 `volunteerID` 已变更为接收方。

4. 演示数据中可用的外键：

   - 志愿者：`vol-0001`、`vol-0002`
   - 投喂点：`point-feed-0001`
   - 投喂任务：`shift-0001`（已完成）、`shift-0002`（待执行，负责人 `vol-0001`）、`shift-0003`（已排班，负责人 `vol-0002`）
   - 待确认交接：`handover-0001`（`vol-0001` → `vol-0002`，关联 `shift-0002`）
